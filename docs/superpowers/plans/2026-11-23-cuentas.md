# Cuentas de usuario — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Cada persona entra con correo o Google y tiene su propia cartera guardada en Postgres, accesible desde cualquier dispositivo.

**Architecture:** Clerk protege todas las páginas y `/api/*` mediante middleware. Un repositorio SQL (`lib/server/repo.ts`) es el único que toca la base de datos y recibe siempre `userId` como primer argumento; las rutas lo obtienen de `auth()`. El cliente sustituye `localStorage` por llamadas a `/api/portfolio*` con actualizaciones optimistas.

**Tech Stack:** Next.js 15.5.29, `@clerk/nextjs@7.9.25`, `@neondatabase/serverless@1.2.0`, Node test runner.

**Spec:** `docs/superpowers/specs/2026-11-23-cuentas-design.md`

## Global Constraints

- Clerk en modo desarrollo sobre `cartera-wine-two.vercel.app`; nada del código debe asumir un dominio propio.
- Registro abierto a quien tenga el enlace; la web lleva `noindex` y `robots.txt` con `Disallow: /`.
- Toda consulta SQL de datos de usuario incluye `user_id = $userId`; `userId` sale solo de `auth()` en servidor.
- Variables de entorno: `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY`, `DATABASE_URL` (las aprovisiona el Marketplace).
- Sin ORM. Textos de interfaz en español.

## Review Focus

1. Operación con campos inválidos o manipulados (cantidad ≤ 0, fecha futura, tipo distinto de buy/sell, moneda que no es de 3 letras) → 400 con mensaje, nada se guarda. Test en Task 1.
2. Un usuario intenta borrar/editar el `id` de una operación de otro → no afecta a filas ajenas (la consulta filtra por `user_id`). Test en Task 1.
3. Importación de una cartera local grande (≥ 500 operaciones) o con filas inválidas → se rechaza entera con el número de fila; no se guarda a medias. Test en Task 1.
4. Fallo de red al guardar → la interfaz revierte el cambio optimista y muestra aviso. Cubierto en Task 4 (lógica pura `applyOptimistic`).
5. Usuario sin sesión llama a `/api/quotes` → 401, no precios. Verificación en Task 5.

### Task 1: Validación y repositorio SQL

**Files:**
- Create: `lib/validate.ts`, `lib/server/db.ts`, `lib/server/repo.ts`, `db/migrations/001_init.sql`, `scripts/migrate.mjs`
- Test: `tests/validate.test.ts`, `tests/repo.test.ts`

**Interfaces:**
- Produces:
  - `validateTx(input: unknown): { ok: true; tx: Transaction } | { ok: false; error: string }` (en `lib/validate.ts`, puro)
  - `validateSettings(input: unknown): { ok: true; settings: Settings } | { ok: false; error: string }`
  - `interface Db { query(text: string, params: unknown[]): Promise<Record<string, unknown>[]>; transaction(qs: { text: string; params: unknown[] }[]): Promise<void> }`
  - `getDb(): Db` (en `lib/server/db.ts`, envuelve `neon(process.env.DATABASE_URL)` con `sql.query` y `sql.transaction`)
  - En `lib/server/repo.ts`, todas con `sql: Db` inyectable para tests:
    - `getPortfolio(sql, userId): Promise<{ txs: Transaction[]; settings: Settings }>`
    - `upsertTx(sql, userId, tx: Transaction): Promise<void>`
    - `deleteTx(sql, userId, id: string): Promise<void>`
    - `saveSettings(sql, userId, s: Settings): Promise<void>`
    - `importTxs(sql, userId, txs: Transaction[], mode: "append" | "replace"): Promise<number>`
    - `deleteUserData(sql, userId): Promise<void>`
  - `Settings` se mueve a `lib/types.ts`: `{ base: string; colorPnl: boolean }`.
